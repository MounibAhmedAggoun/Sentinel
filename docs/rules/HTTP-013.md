# HTTP-013: Content-Security-Policy observed without an object-src restriction

- **Area:** http
- **Severity:** informational

## What is observed

The Content-Security-Policy has no object-src directive and no default-src to fall back on.

## Why it can matter

The object-src directive limits where plugin content, such as &lt;object&gt; and &lt;embed&gt; elements, may load from. When a policy has neither object-src nor default-src, nothing limits it, so a page that gets injected content may still load a plugin resource. Most sites no longer need plugins, and object-src 'none' says so.

## False positives

object-src falls back to default-src, so Sentinel reports this only when neither directive is present. A site that really uses plugin content needs a more specific value than none. Sentinel reads one response, and a policy set through a meta tag is not seen. Browsers have dropped most plugins, so the practical difference is smaller than it once was.

## How to fix

### nginx

```
# Add the directive to your existing policy. Do not send a second header.
add_header Content-Security-Policy "default-src 'self'; object-src 'none'" always;
```

### Apache

```
# Needs mod_headers. Add the directive to your existing policy.
Header always set Content-Security-Policy "default-src 'self'; object-src 'none'"
```

### Caddy

```
header Content-Security-Policy "default-src 'self'; object-src 'none'"
```

### Express

```
app.use((req, res, next) => {
  res.setHeader('Content-Security-Policy', "default-src 'self'; object-src 'none'");
  next();
});
```
